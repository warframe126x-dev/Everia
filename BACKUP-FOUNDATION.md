# v1.0 Stage 1C backup foundation

Live data remains in Electron's existing `%APPDATA%\Everia` profile. No renderer origin or live-data migration is performed.

The `.everiabackup` file is UTF-8 JSON with top-level `manifest`, `data`, and `assets`. Schema `1` is independent of the app version. `manifest` records `format`, `schema`, `appVersion`, `createdAt`, record/asset counts, asset inventory with SHA-256 digests, and a SHA-256 digest of the JSON serialization of `{data,assets}`. `data` contains validated library records and `settings` (theme, sorts, views). Each asset entry contains its IndexedDB store, ID, MIME type, byte count, SHA-256, and canonical base64 bytes. Both `covers` and `wallpapers` stores are exported, including unreferenced local images. No archive extraction or filesystem paths appear in a backup. Future schemas require an explicit import handler; newer unknown schemas fail closed.

Credentials are excluded. Provider references embedded in library records remain included. Windows `safeStorage`/DPAPI secrets are bound to an OS user and cannot be promised after OS loss; restore requires re-entry where necessary. Window geometry and Chromium caches are excluded.

`src/backup.ts` validates the logical data, record schema, settings, referenced assets and decoded image bytes. `electron/backup-store.cjs` imposes file, record, asset and total-byte bounds, checks hashes again, writes a staged file, fsyncs, re-reads/verifies, then renames to a unique final name. Failed creation does not remove previous backups. A selected missing destination fails rather than falling back. The default destination is the OS Documents folder's `Everia Backups` child; config and last success/failure are stored in `userData/backup-config.v1.json`.

Restore validates the incoming file before any mutation, captures the existing logical backup and original localStorage strings in `userData/restore-journal.v1.json`, commits IndexedDB assets in one transaction and the four localStorage keys, then exports and compares the committed logical payload. If any step fails, or if the app restarts while a journal exists, it restores the prior assets and exact localStorage strings before showing the library. A damaged recovery journal blocks startup and is retained for repair. The old state is not intentionally deleted before validation; the journal is removed only after read-back or rollback completes. A backup is a logical recovery format, not a snapshot of provider credentials.

The automatic core runs at startup after UI initialization and hourly while the app is open when the last successful backup is at least 24 hours old. No background process runs while Everia is closed. `everiaBackup` preload IPC exposes destination selection, enable/disable, due status, manual write and selected restore for the later Settings UI. A failed attempt records `lastFailure` and retains `lastSuccess` so the next hourly/use opportunity retries. Retention is computed after a validated replacement: newest representative for each of the latest seven UTC dates, four ISO weeks and six UTC months. One snapshot can satisfy multiple tiers. The most recent validated backup is always retained; unrelated or unverifiable files are untouched.

This stage does not expose the final Settings surface. The production UI remains the approved v0.9 layout. Backup tests use in-memory IndexedDB and injected failures; the Windows Stage 1C workflow tests the packaged actual save and restart behavior separately.
